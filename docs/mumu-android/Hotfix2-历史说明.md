# Hotfix2：四类塔楼、固定塔序及完成后返回修复

## 未开播的根因

上次 55 指令回放包含皇家厨师。旧原生观察器按编号前缀 35 筛塔，只记录到对方三座普通塔；皇家厨师的国王塔和两座副塔被漏记。必须六塔的检查因此拒绝预演，错误 119 的空输出又被旧提示误报成 excessive observation。

MuMu 现在生成有哈希记录的独立适配头，按本局已验证的所属玩家、完整编号和坐标匹配，覆盖公主塔、炮塔、匕首女爵和皇家厨师。原始 C++、游戏库、指令和安全校验保持不变。缺塔、重复塔、未知编号、错误坐标或错误生命组件仍拒绝开播。空结果与过大结果分别报告，保留原生错误码和实际观察塔数。

## 1734 是塔位误配，并非对局差异

| 玩家 | 比较项 | 网页血量 | 原生血量 | 差值 |
| --- | --- | ---: | ---: | ---: |
| owner0 | 国王塔 | 7728 | 7728 | 0 |
| owner0 | princess0，x3500 | 3408 | 3408 | 0 |
| owner0 | princess1，x14500 | 4275 | 4275 | 0 |
| owner1 | 皇家厨师国王塔 | 7549 | 7549 | 0 |
| owner1 | 剩余副塔 | 2115 | 2115 | 0 |
| owner1 | 原生记录已摧毁副塔 | 0 | 0 | 0 |

旧版对 owner0 又做了一次水平镜像，算成 |3408−4275| + |4275−3408| = 1734。新比较器对双方均使用固定出生顺序：princess0 对 x3500，princess1 对 x14500；不会排序、择优交换或互换双方。固定顺序与视角翻转不能混为一谈。原先关于 owner0 应额外镜像的解释不成立，已纠正。

双方六塔分别算绝对差后求和，不以双方或三塔总血量相减抵消。若故意把这两个网页值对调，检查仍报 1734。此前两份真实回放记录仍通过；按旧镜像假设编写的模拟测试已依据本次双塔存活的实机证据纠正。

单塔存活仍保留原战报的压缩列表规则：网页单元素列表不能证明毁塔侧，原生必须有毁塔回执，不能将缺少记录猜成零。该局右侧副塔在原生确实有摧毁回执，但不因此宣称网页单值证明了原局毁塔侧。

## 所有塔楼采用同一套身份规则

毁塔编号统一按无符号 32 位比较，解决匕首女爵和皇家厨师的带符号编号。国王塔使用各自塔楼配置的实际编号，解决皇家厨师国王塔的特殊 ID。初始化、预演观察、终局血量与战场读取均检查本局配置，六塔、等级、满血、生命组件与清理检查继续有效。

模拟器内独立原生观察器覆盖四类塔楼的 16 种双方组合、96 项异常拒绝及 16 项原生析构委托与恢复。这是隔离内存测试，不能替代 16 种完整真实对局。最新 55 指令皇家厨师回放另做了完整实机播放。

## 播完返回控制台

首次完整测试还发现完成状态与文件所有权交接的竞争：Root 创建的终局记录尚不可读时，服务已看到 complete，可能报权限不足。新版先将本任务记录恢复给应用自身，再发布终局状态；不增加公开读取权限。再次完整播放核验客户端刷新、回到大厅和实际控制台恢复事件。

## 验收与使用

当前 APK 已覆盖安装。53 项针对性主机回归、60 项控制台设备检查通过；同一份原始 55 指令 HTML 完整预演、JSON 往返和可见播放通过，六塔血差 0、种子重试 0 次，客户端刷新并实际返回控制台。具体耗时见验收 JSON。

仅在实际打出猎人，或实际使用可明确归属骷髅帝王的技能，且终局仍不匹配时搜索种子；普通血差不触发。停止匹配按钮保留。匹配终局血量和原始指令不证明全过程的唯一性。
