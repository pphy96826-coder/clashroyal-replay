# 反馈驱动的技能与种子联合搜索

MuMu Android 控制台现在为每个种子保存独立的合法技能分支队列。在原生候选安全释放后，调度器决定继续当前种子、尝试新种子或恢复暂存种子。换种子后重新校准初始牌序，重新枚举技能，不继承另一个种子的技能角色或序号。

首版是可解释的调度基线，尚未使用或训练神经网络，也没有证据表明它已经优于旧算法的同耗时结果。目标是建立可核查的反馈闭环与训练数据，再以相同时间预算比较最佳完整对局的六塔血差。

## 分配依据

记录每个种子的候选次数、完整通过次数、本种子最优血差改善次数、最长已接受指令前缀、连续未改善次数和实际耗时。下一次模拟的手写评分综合平滑后的产出、探索项、指令进展、耗时和停滞惩罚。这个评分不是经过训练的成功概率。

每六次尝试强制探索等待最久的可用种子，避免暂时受阻的区域永久失去机会。切换不删除队列。暂停后的恢复仍从新建原生对局重放前缀，并非恢复游戏内存快照。

## 约束与选择

- 仅源指令完整执行、原生全部接受、引擎已结束的候选参与最终选择。未结束的零血差不能播放。
- 六座塔仍按各塔绝对血差合计评分，沿用既有塔位核验规则；没有新增塔血排序或左右交换。
- 不使用固定 2:20 截点。遇到技能歧义才扩展合法分支；越过现有 HTML 塔血下限约束立即剪枝。
- 只有本轮有限种子池的严格队列全部用尽且没有完整结果，才进入已授权的近似续算。首先新建对局重跑剪枝时六塔血差最小的前缀，随后比较完整结果。
- 达到时间或次数上限不代表所有情况都已尝试。仍有严格分支时，不因预算用尽擅自进入近似续算。
- 已有完整结果时，可用现有“停止匹配，播放当前最优”操作在安全边界选取。正在执行的原生调用先完成归属与释放检查。

## 默认范围

普通 MuMu 回放仅在实际出过猎人、或能够识别骷髅帝王技能时启用多种子调度，沿用原搜索触发条件。默认最多纳入 8 个种子、执行 128 个技能候选，搜索时间软上限 900 秒。软上限在候选边界检查，不中断运行中的原生任务；发牌校准和候选执行耗时计入。原有模块归属数量上限继续生效，保留录像往返与播放核验所需名额。

未达到触发条件的回放仍搜索技能；显式固定种子的诊断请求继续遵守用户锁定。Windows 与 Android 原生独立交付目录的运行流程未改用此 MuMu 调度器。

## 留存数据

每个本机任务的 `adaptive-search.json` 绑定源 HTML 哈希和游戏进程代际，保存：

1. 每个种子的剩余技能选择队列、已执行选择和剪枝记录。
2. 每次调度前各候选种子的反馈特征、评分、动作及原因。
3. 本次尝试实际耗时、完整性结果、终局血差及完整结果改善量。
4. 所选完整候选的原生证据文件、停止原因、预算是否用尽。

原生技能角色、候选列表与执行回执保留在对应 `*-source-execution.json` 中。快照用于审计和后续训练；当前支持同一次搜索内恢复暂存队列，不会在客户端重启后复用旧指针，也尚未实现跨进程恢复搜索。

未来模型可预测“下一批搜索找到更优完整结果的概率与改善量 / 耗时”。训练时应按回放划分训练和验证集，保留探索样本，并用相同墙钟预算的最终血差、完整对局获得率和停止耗时评估。当前未训练模型，不能将调度分数解释为模型置信度。

## 回归与设备验收

新增测试覆盖每种子独立技能选择、暂存恢复、耗时反馈、完整性门槛、取消与接受最优、时间和原生归属预算、有限搜索范围以及最近剪枝前缀续算顺序。

`SkillTargetTests` 的 `mode=adaptive` 是源哈希绑定的本机原生测试，限制为 2 个种子、12 个技能候选及 420 秒软上限，不提交播放场景。这个测试用于验证调度、校准和分支执行，不能单独证明误差降低或整局播放通过。
