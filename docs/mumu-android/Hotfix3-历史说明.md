# Hotfix3：先匹配技能，再匹配随机种子

回放 02JYPPC02YUL 含 85 条指令、16 次技能、3 次猎人出牌。此前一个完整合法分支已被原生接受，但旧技能搜索要求先匹配终局血量才能进入种子搜索，导致两项搜索互相卡住。切后台超过 120 秒还会被取消，错误提示没有解释清楚。

## 新搜索顺序

1. 固定初始随机种子，按原生报告的技能目标分歧探索组合。全部 85 条指令被接受、时间与原始指令一致且确实到达原生终局的组合才参加评选。
2. 用双方六座塔分别计算绝对血差，再合计。选择合计最小的技能组合；相等时保留先完成者，零差可提前结束。达到安全预算或主动停止时保留已经完整验证的最佳结果，不宣称穷尽未知组合或证明原局唯一。
3. 技能阶段完成后固定这组逐事件目标选择，再校准和搜索新随机种子。每次都由原生引擎重新解析目标，不复用指针。失效或出现未选定分歧的种子被拒绝，不在种子阶段改换技能组合。
4. 种子搜索只在实际打出猎人，或明确使用骷髅帝王技能且终局不符时触发。单纯卡组包含这些卡不会触发。随机种子与终局优劣没有单调关系，不使用二分法。

## 停止、恢复与稳定性

技能搜索和种子搜索只要已有完整结果，就能点“停止匹配，播放当前最优”。请求绑定本份 HTML 和客户端进程代际，等当前原生步骤安全结束，再核验整局 JSON 后播放。失败候选、未结束模拟和技能前缀不能成为最优。

准备中切到控制台或浏览器只暂停；回到同一客户端前台空闲大厅继续，不再两分钟自动取消。进程和代码校验继续保留。原有 256 个回执上限保留，提前预留 4 个位置给正式播放的 JSON、场景及终局检查。

本轮 dev30 曾在调试器函数调用时遇到空地址异常，主线程 PC 位于 MuMu 翻译代码；成功样本则在系统等待位置。dev31 在任何表达式、分配或组件加载之前先观察主线程：必须位于宿主 libc 映射且是系统调用等待点；否则先分离并重新采样同一代际，最多 20 次。不会修改寄存器或 PC，不重试失败函数，不跳过游戏库哈希和原生合法性保护。未找到合适位置则明确停止。

运行环境先在临时目录解包并完整校验，再发布使用；不完整旧目录保留后重新准备。此恢复机制独立实测于 dev28，不能当成 dev31 新算法的整局证明。

交付 APK 为 2026.10.21-mumu-dev32，已覆盖安装到本机原实例。完整实机测试在 dev31 进行：本份原始 HTML 完整预演、JSON 往返及实际播放通过，85 条指令、16 次技能和 3 次猎人均保留。技能候选尝试 37 次，技能阶段选中血差 1492；最终标签 same_towers、六塔血差 1492。这只证明已试完整候选中的最优，不把近似结果标为精确还原。

dev32 只修正了一处进度消息参数，使技能阶段显示技能组合及当前血差，进入种子阶段才显示种子次数。对比 APK 所有成员、运行时所有文件及归一化语法树，确认引擎、排序、技能选择、时序、安全及播放逻辑均与 dev31 一致；DEX 和原生库也逐字节相同。dev32 另已覆盖安装，完整环境已校验，85 指令解析和 60 项控制台检查通过，两类进度消息单独核验。具体证据列在验收 JSON。
