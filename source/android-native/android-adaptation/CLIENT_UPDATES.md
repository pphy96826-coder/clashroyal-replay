# 游戏更新与适配

## 2026-10-30 hotfix77：38.5.2 已完成本机整局验收

已在作者选定的 Mac + MuMu Pro 安卓1验证腾讯 38.5.2（完整库哈希见下文）。63 条源操作全部执行，原生 JSON 往返保持指令一致，随后实际游戏画面推进至原生终局 tick 4551，渲染驱动错误为 0。预演、网页与可见终局的六塔血量总差均为 0，其中包含一座被摧毁的塔；终局判断和塔缺失证据没有被修改。双方溢出圣水一致，本次没有搜索替代种子。

安装包通过完整库哈希自动选择内置的 38.4.2 或 38.5.2 适配。两个适配的 Python 模块、原生源码、对象布局和代码契约相互隔离，更新客户端后重新绑定进程、资源、工作线程及实际代码指纹，不复用旧句柄。未知哈希继续只生成重定位诊断，不自动执行未验证接口，也不从网络下载适配代码。

38.5.2 的变化还包括运行时导入表与静态重定位记录相差一个表项；malloc/free 与三个线程同步函数均按现场真实目标逐项核对。仅改库大小、版本号或统一给所有字段加 8 均不足以适配。

验收范围是上述一台 MuMu Pro 与一场完整对局。旧版适配保留；朋友的虚拟大师 ROM、其他实体机和 Windows 专用翻译层没有本次实机验收。下文保留适配调查过程，标为 pending 的历史文件不参与运行时选择；最终启用契约使用 `.approved.json`。

控制台在每次准备或播放前，重新读取当前安装 APK 的完整 ARM64 库哈希，不沿用上次的检查结果。库读取上限为 128 MiB，实际读取量必须与 ZIP 声明相符；版本号和文件大小均不能单独证明兼容。

- 引擎完整哈希仍受当前运行时支持：继续现有的当前进程绑定、资源准备及完整回放验证流程。
- 引擎未知：在进入原生调用前停止，将版本、哈希、大小及需要新适配的状态保存到 `client-compatibility.json`。该报告随诊断导出。不会将旧地址或旧进程句柄用于新引擎。
- 不自动从网络下载可执行适配，不把不匹配直接加入白名单。新引擎必须完成函数、对象布局、资源和序列化适配，再通过完整执行、JSON 往返、可见播放验证后才能启用。

本机可对用户自己的 APK 自动生成更新审计：

```
python3 scripts/audit_client_update.py /path/to/user.apk --output /new/private/report.json
```

此命令只读取文件，检查 ARM64 ELF、完整哈希及原适配的 61 个指纹位置。即使全部采样指纹一致，未知完整哈希也不会自动批准。诊断不包含 APK 内容，不应公开分发用户的客户端 APK。

## 自动重定位（2026-10-30）

未知库现在会在控制台准备入口自动触发 `ClientRelocator`，不再只比较版本号后退出。参考签名来自已审计 APK，由 `scripts/build_relocation_reference.py` 生成并随控制台打包；不包含游戏字节、进程地址、APK 或原任务句柄。

扫描仅在 ARM64 ELF 的可执行加载段内按指令边界进行。对 B/BL、ADR/ADRP、条件分支和 PC 相对字面量加载，保留指令类型及寄存器，只规范化可变地址部分；一般立即数、结构体字段偏移不做模糊屏蔽。完整规范化窗口相同时才产生候选。直接调用关系可以剔除不一致的重复候选，但不能把候选当成已验证函数。超过匹配上限的模式始终保留歧义。

独立 JVM 测试覆盖移动函数、分支地址变化、重复模式、调用图排除、错误架构、非法引用以及不能屏蔽字段偏移。当前 38.5.2 测得 21 处唯一候选、12 处歧义、28 处未定位；这还没有覆盖所有对象布局、静态数据引用、运行时变换和序列化接口。报告明确保存 `object_layout_verified=false`、`native_execution_allowed=false`。

因此这一版已完成自动重定位诊断，但尚未恢复 38.5.2 的原生播放。不能把扫描或 APK 构建成功称为新版本播放适配完成。

## 38.5.2 实际接口差异核对

当前已对选定安卓1做只读检查，重新核对安装 APK 哈希、进程启动时间、映射和已有权限。每段代码读取两次确认稳定，总读取量受 64 KiB 限制；没有附加调试器、执行游戏函数、修改游戏内存或重启模拟器。

已确认的变化包括：

- 回放 Domain 原分配 576 字节，新版原生调用处为 584 字节。旧版三处、新版六处明确的分配调用均一致。
- Domain 的 `0x220` 字段移到 `0x228`，加载、推进、构造和清理四个入口交叉印证。加载和推进函数除这组字段引用及地址重定位外，规范化指令流一致。
- Avatar 的手牌索引入口由 `0x218` 移到 `0x220`，当前圣水由 `0x300` 移到 `0x308`。消耗、获得、溢出字段已进一步通过技能扣水和上限增水函数的读写路径确认，分别由 `0x348/0x34c/0x350` 移到 `0x350/0x354/0x358`；当前进程双读与安装包字节一致。其他对象和字段仍不能据此直接全部加 8。
- 场景插值与推进回调槽位分别从 `0xb08` / `0xb10` 变为 `0xb28` / `0xb30`。表起点由构造函数独立定位，再依据方法身份查槽位；不能用新方法地址减去旧槽位来猜表起点。
- 新资源入口已找到，并只读确认服务对象、管理器及工作线程存在。这不代表组件已经能够执行。

这些事实记录在 `profiles/client-update-38.5.2.pending.json`，它是未完成的适配调查记录，**不参与运行时批准，也不是可安装的播放修复**。

新增复用工具：`read_client_candidates.py` 进行受限代码采样；`audit_runtime_layout.py` 区分地址变化与对象字段变化；`audit_object_allocation.py` 核对构造调用前的真实分配大小；`audit_vtable_layout.py` 查找回调槽位。调用图分析也已修正：函数内部的入口不会直接继承旧偏移，必须重新找到唯一指纹。相关测试覆盖字段移动、寄存器复用、对象大小变化、槽位插入、重复候选、进程读取预算及不完整采样。

当前还没有完成 38.5.2 的完整执行与可见播放验收；已有诊断 APK 不应被称为新版播放修复包。界面措辞也已由“新游戏引擎”改为“客户端原生接口尚未验证”，避免将库变化直接等同于基本对战规则变化。

圣水读取已在当前拥有源码中集中到 `runtime-source/official-web-replay/client_layout.h`：终局、检查点和溢出窗口共用字段定义，四项顺序保持为当前、消耗、获得、溢出。合成内存测试故意令两个版本的偏移互相冲突，确认不会误读其他字段。当前获准执行的布局仍是 38.4.2，加入 38.5.2 的已确认字段不会自动批准整个适配。

同时恢复了当前嵌入运行时的拥有源码作为后续修改基线，修复刷新脚本引用不存在目录的问题。本次重新打包后实际只改变 `source_execution.h` 和新增 `client_layout.h` 两个成员；逐成员哈希核验确认技能搜索、种子搜索和既有原生契约均未回退。
